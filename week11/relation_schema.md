# 第 11 周 · 关系 Schema 设计与零样本验证（周一产出）

## 1. 背景判断

第 8—10 周微调的是**实体 schema**（技能 / 学历 / 经验年限 / 岗位名称 / 语言能力 / 知识领域），
模型从未见过招聘领域的关系标注。因此本周关系抽取属于"换任务"推理，预期精度低于第 10 周
实体抽取。本周目标不是刷关系 F1，而是跑通
**关系抽取 → 三元组解析 → NetworkX 建图 → PyEcharts 可视化** 的完整流水线，
让聚合后的结构信号成为图谱的核心价值。

## 2. 嵌套 Schema 设计

UIE 的关系抽取使用嵌套字典：键为抽取主体，值为该主体对应的关系类型列表。
输出中每个主体实体的 `relations` 字段嵌套关系类型和对应的客体实体。
跨任务抽取时，schema 支持实体类型与关系类型混合嵌套，底层 schema 树按层级逐层遍历预测。

针对"岗位—技能/学历/经验"，计划书原始设计为：

```python
schema = {
    '岗位': ['要求技能', '要求学历', '要求经验'],
    '技能': ['关联岗位']
}
```

把"技能"也作为主体的原因：如果只有岗位指向技能，技能节点在图谱中会变成纯叶子节点，
没有出边；加上"技能→关联岗位"的反向关系，后续做"某个技能关联了哪些岗位"的查询时，
技能节点才有可用的结构信息。

**两处必要修正**（对齐第 10 周 checkpoint 的实际训练名）：

1. 实体键名必须用 checkpoint 训练过的 `岗位名称`（而非 `岗位`），否则实体层就不会触发；
2. 关系名是零样本 prompt，不受训练字段名约束，可用自然语言表述。

## 3. 零样本验证（三组变体）

模型：`week9-10/checkpoint/uie_jd_v2`（CPU，position_prob=0.5）。
文本：计划书指定的固定验证句 + 从第 8 周语料 `corpus_week8.txt` 挑选的 5 条信息齐全 JD，共 6 条。
脚本：`week11/scripts/relation_zeroshot.py`，原始输出：`week11/logs/relation_zeroshot.json`。

| 变体 | schema | 实体数 | 关系类型触发 | 三元组数 | 用时 |
|---|---|---:|---:|---:|---:|
| A 完整三关系（计划书原名） | 岗位名称→[要求技能, 要求学历, 要求经验]；技能→[关联岗位] | 33 | 6 | 9 | 12.1s |
| B 仅一条关系 | 岗位名称→[要求技能] | 2 | 2 | 5 | 1.3s |
| C 关系名口语化 | 岗位名称→[技能, 学历, 经验] | 2 | 6 | 12 | 2.2s |

典型输出（固定验证句，schema A）：

```json
{"岗位名称": [{"text": "高级Java开发工程师", "probability": 0.438,
  "relations": {
    "要求技能": [{"text": "后端开发", "probability": 0.397}],
    "要求学历": [{"text": "本科", "probability": 0.987}],
    "要求经验": [{"text": "3年以上", "probability": 0.884}]}}],
 "技能": [{"text": "Spring Boot和MySQL", "probability": 0.907},
          {"text": "后端开发", "probability": 0.732}]}
```

典型输出（同一句，schema C）：

```json
{"岗位名称": [{"text": "高级Java开发工程师",
  "relations": {
    "技能": [{"text": "后端开发", "probability": 0.624},
             {"text": "Spring Boot和MySQL", "probability": 0.591}],
    "学历": [{"text": "本科", "probability": 0.995}],
    "经验": [{"text": "3年以上", "probability": 0.852}]}}]}
```

嵌入式硬件工程师 JD（长文本）在 schema A/C 下均抽出 4~5 条技能关系、1 条学历关系
（"本科"，概率 0.998）、1~2 条经验关系（"2年以上"，概率 0.96）。

## 4. 是否可用的判断

结论：**关系抽取部分可用，但按计划书口径需要同时启用降级方案。**

可用的证据：

- `relations` 字段确实被填充，客体实体与原文一致，学历/经验关系概率高（0.85~0.998）；
- 关系名口语化（C）比"要求技能"式命名（A）触发更充分：6 条文本 12 个三元组 vs 9 个，
  且 C 能把"A 漏掉的 Spring Boot 和 MySQL"正确挂到岗位下（A 中该客体只作为独立技能实体出现）。

不可靠的证据：

1. **触发稀疏的根源是主体覆盖**：三条测试文本 relation 全部为 0，原因是段落里没有抽到
   "岗位名称"实体。第 10 周评估显示 `岗位名称` 字段仅覆盖 67/600 条训练文本、
   测试集只有 8/37 条唯一文本含岗位实体——即使关系层 100% 正确，显式关系图谱的主体也只有个位数节点。
2. **反向关系未触发**：schema A 中"技能→关联岗位"在全部 6 条文本上 0 次触发（技能的
   `relations` 始终为空），技能节点仍然是纯叶子。
3. **个别关系有噪声**：如"经验→配合"（概率 0.48 的误触发），客体明显不是经验表述。

调优动作（按计划书"把关系名改为更贴近 JD 原文的表述"的指引）：

- 主体键名固定为 `岗位名称`，关系名采用 C 组口语化命名（技能 / 学历 / 经验）；
- 保留"技能"作为主体收集技能实体（用于节点表），但放弃"关联岗位"反向关系——它不触发，
  反向查询改由建图后在 NetworkX 侧对边做逆邻接统计实现，效果等价。

## 5. 本周采用方案（周二起执行）

- **主链路**：批量关系抽取使用 schema
  `{"岗位名称": ["技能", "学历", "经验"], "技能": ["关联岗位"]}`，
  显式三元组进入 `triples.json`，来源标记 `uie_relation`；
- **降级补充**（计划书"选择一"）：同一文本内共现的 岗位名称×技能 实体对补为
  `cooccur` 关系，保证图谱有内容、有结构；
- 报告中明确声明：**共现关系是近似方案，精度上限低于显式关系抽取**；图谱价值以
  聚合信号（高频技能排序）为主，不宣称单条关系的正确率。
- 若后续有 100~200 条关系标注数据，可在第 12 周回到 `label_studio.py --task_type ext`
  补标并做关系 schema 轻量微调（本周不硬做，避免挤占可视化时间）。
